# One conversation, native review workers

Execute the supplied `collect_command` with `--as-file` and Read its complete `collect_result_file`. This content-addressed immutable UTF-8 reading view retains all feedback, source-specific errors and repair commands, and explains any lossless long-text segmentation. The terminal locator is ASCII; do not capture, decode, parse/reprint or save Python stdout through PowerShell. `REPAIR_REQUIRED` means repair only the listed entries in their owned answer files and preserve successful workers, not restart all packets. Existing blank templates are not submitted responses. Feedback files are not semantic approval; ordinary collection and final validation remain unchanged. Legacy collection without `--as-file` keeps its direct JSON output.

For recovery or a submission-count check, run the returned `progress_command` (`review-status`). It reads the guarded current packets without merging or approving answers and separately lists no-fitting-cluster responses requiring the parent. Do not write helper programs or count files manually. Actively use TaskOutput with at most45 seconds per wait, or the supplied `wait_command`; do not end the turn solely to wait for notifications. On each resumable timeout inspect pending host task IDs using `native_task_health`. Running stays running; file age/timeout does not prove failure. Only an explicit host terminal failure/aborted/502/connection error AND confirmed termination of the old writer permits same-model, same-window retry of that failed worker, at most2 retries; read its current answer and preserve completed entries. Never rerun successful workers or change networking/security settings. At the limit retain checkpoints and report. `ALL_RESPONDED` is not semantic acceptance and still requires host-task completion, collection and ordinary validation.

Source collection likewise identifies exact `missing_source_ids`, `unexpected_source_ids`, `repeated_source_ids`, `incomplete_review_ids` and `repair_source_ids`; `repair_readable_input_file` contains only failing assigned rows, literal candidates, their current answer/errors and blank reserved fields. Read this (or the complete combined small tail when supplied) plus the current answer file, not the whole original material packet. Fix only those entries/remove extras, preserve other explicit answers, then collect normally. Source evidence errors use this same scoped path. Context creation neither edits answers/parent nor accepts a source; stale inputs are rejected before creating repair feedback.

On WorkBuddy, every native Agent call must retain `run_in_background=true` from the returned `workbuddy_agent_input`; omitting it causes synchronous waiting. Use the complete argument object, not only its prompt/model. This also applies after resuming or compressing context. Only explicit host rejection permits the documented synchronous fallback.

If the host explicitly says `TaskOutput` does not wait for teammates, use the returned `wait_command` (`review-wait`) instead of fixed `Start-Sleep` calls. This read-only controller wait returns as soon as all guarded responses are present or inputs become stale, with a maximum of 45 seconds per call. `WAITING_RESPONSES` is a resumable timeout, not failure; continue native waiting or the supplied command. It does not hold the workflow lock, launch models, approve answers, or confirm host-task completion. After `ALL_RESPONDED`, confirm the native tasks have finished, then collect. Never use a minutes-long sleep or write a custom polling program.

`RESPONSE_ERRORS_PRESENT` means a worker changed its answer file but the file cannot be parsed or its ID containers are structurally inconsistent. Once that native task has ended, run `collect` immediately to receive the exact worker-scoped repair error; do not keep waiting as though no answer was submitted. Successful workers remain untouched.

Worker answer files contain only editable semantic fields. Their complete contracts and cluster choices live in the guarded task file; read them there, never copy this fixed material into the answer. Workflow IDs, scope tags and input hashes stay in the immutable dispatch. The script reconstructs the parent submission only after checking current input hashes, worker paths, exact ID coverage and evidence. Do not copy or invent binding metadata in worker answers. Explicit conflicting metadata is still rejected; old bound worker formats remain supported. This exception applies only to native worker files, not the main controller's editable submissions.

Start every returned job before waiting for any result. On WorkBuddy, when native background tasks are supported, use each job's `workbuddy_agent_input` unchanged (`run_in_background=true`, inherited model). Prefer issuing all those background Agent calls in one tool-call turn when supported, instead of taking a new model turn between every start. Record the returned task IDs, then wait using `TaskOutput` or native completion notifications. If the host rejects grouped calls, start them individually before waiting. If background tasks are unavailable, invoke all synchronous Agent calls in the same tool-call turn. Never execute one entire packet before launching the next. A queued or running task is not complete. Do not return a final answer while native work remains outstanding. These arguments do not authorize new CLI processes, model settings changes or another model.

Use only the host's native Agent tool and inherit the main conversation's model. This is an execution path within the Skill, not permission to spawn extra CLI processes or use another model. The controller only transports files; all semantic decisions still require the assigned agent to read the actual evidence.

Native task files normally include a bounded single-read bundle: complete rules, all assigned materials and the initial semantic submission are in that file. Read the whole task file once; do not reopen the separate input or initial answer merely to fetch the same content. `reading_bundle_file` in the immutable job identifies this mode. All original input artifacts and answer paths remain, and task hashes guard the bundled content before collection. If it cannot safely fit, the dispatcher retains the original multi-file task without clipping anything. On a repair request, read the current answer file and preserve other completed entries; the embedded initial submission is not a current answer. This changes reading transport only, never supplies a decision or removes a semantic check.

At `source_review`, a `cluster_assignment_review` residual packet, or `final_excerpt_review`, run:

With `--as-file`, the terminal returns an ASCII JSON locator. Read its complete `handoff_file` directly with the host file reader: this guarded UTF-8 file contains the full `jobs`, exact native arguments, wait and collect commands. Do not redirect Python output to PowerShell text, parse/reprint the handoff, count prompts with a helper, or create conversion programs. This avoids shell Unicode recoding while preserving all values. Legacy callers omitting `--as-file` still receive the full direct result.

```powershell
<python> scripts/film_workflow.py review-dispatch --workspace <workspace> --as-file
```

The returned `jobs` contain short prompts pointing to self-contained task files for up to 16 workers. Source review normally uses at most 30 items per worker; if a small tail would otherwise require another wave and the entire remaining queue fits within 40 per worker, the script evenly distributes it in this wave. Assignment review similarly uses 12 normally and at most 14 to absorb a small tail; final excerpt review uses 30 normally and at most 35. Larger queues retain the normal packet sizes and continue in later waves. An explicit `--per-worker` sets a fixed cap (source maximum 40, assignment maximum 14, final maximum 35). This only schedules unresolved items and never drops them or supplies judgments. Batch native calls in one turn when supported; background starts may be issued one at a time, but all must be issued before waiting for results. The host owns actual scheduling and concurrency. This is a requested fan-out, not a guarantee of 16 simultaneous workers. If the host explicitly rejects that many jobs, use its supported smaller count; do not launch external processes to bypass its limits. For WorkBuddy's Agent tool use `subagent_type="general-purpose"`, `model="default"`; never use `lite`, `reasoning`, or a different named model. Allow workers enough turns to read, use lookup where necessary, and fill their files. Do not spawn grandchildren. Wait for the host's completion notifications or its native task-output tool; do not poll files in a tight loop.

Children write only their individual review files. They must read every assigned item, use the prefilled templates, and return only a short completion message. They may run the read-only controller `lookup` for source text. They must not run `advance`, `status`, `init`, `review-dispatch`, or `review-collect`, or modify the Skill. Only at final excerpt review, a repairable excerpt is returned in `excerpt_repairs` and removed from `reviews`; after re-rendering, the changed excerpt returns for review with a new fingerprint. Source review always keeps every assigned source ID in `reviews`.

Final-review repair packets preserve an earlier incomplete answer only when its workflow and item fingerprint still match. Read the evidence and fix the listed `submission_errors`; a prefilled answer is not approval or a newly submitted response. Unchanged prefills do not count as responses in the waiting status. Do not erase unaffected fields or reconstruct the whole answer unnecessarily. Changed excerpts and other runs never inherit old answers, and the guarded ledger plus ordinary final validation still apply.

Assignment repair packets can also contain a controller-prefilled failed answer with a nonempty old reason. Per-item answer digests prevent these unchanged values from counting as new responses, even if another item in the same worker file changed. Collection returns `unchanged_assignment_prefill` against only that ID without writing the parent. Read its current evidence/errors and actually repair the failed fields, or use a guarded explicit current prior-proposal confirmation when offered. Merely returning the same failed form is neither a new review nor acceptance.

Representative final inputs explicitly carry `representative_selection:true`. Each group gets only remaining candidate slots, at most 10 different sources; pending reservations are not confirmations. If this candidate is not a definite supporting representative, use `reviews[view_id]` with `decision:"not_selected"`, a current excerpt `evidence_candidate_index`, and a concrete `reason`. This means unused for this group, not invalid, dropped, reassigned or approved. It does not require exhaustive re-excerpt or other-cluster checks. Scripts preserve the record and try a replacement; completed groups stop. All keep gates and current fingerprint checks remain. Other legacy inputs do not allow this disposition.

Explicit `excerpt_repairs` are stored with script-owned per-view raw-source/definition/config/repair bindings. An unrelated member move may rebind still-identical literal cuts without erasing them; changed or unbound requests are not carried and the old submission is archived. This carries extraction requests only, not semantic keep decisions. Always advance and validate the newly rendered current excerpt; never treat this metadata as approval or edit it manually.

When genuinely checking an explicit reassignment, read the guarded current cluster definitions on demand; do not invent a claim that other clusters were checked. Submit `reassignment_requests[view_id]` with proposed cluster, current excerpt evidence index and reason; remove that ID from other containers. This remains a proposal with the existing parent repair contract. Representative mode should not manufacture reassignment work for unused candidates. Children never edit assignments.

Collection preserves other answers and sends the proposal to `final_assignment_repair`. For primary-only moves, first use `operator_contract.scoped_patch.prepare_command`, not a full-table read. The prepared patch exposes only pending sources, exact per-source passage and target menus, their current requests and existing entries, plus current definitions. Read all returned reading files and definitions; fill cluster, local stance, concrete reason, passage indexes and a separate target index in the semantic-only patch. If no candidate fits, lookup and supply literal text while clearing the conflicting index. The returned apply command validates the entire patch and merges once under the workflow lock, preserving unrelated entries and metadata; malformed, stale or partially invalid patches do not write the canonical table. Duplicate applications do not rewrite it, and exact crash-after-commit recovery only restores transaction bookkeeping. This is mechanical transport, not approval of the AI judgment. A source with an affected existing secondary route retains the original explicit scoped edit path for now; edits to one file must be sequential. Alternatively, reject a proposal with a complete, valid final judgment in `optional_rejection_review_file`, plus `reassignment_request_resolution="reject_request"` and a specific `reassignment_request_reason`. A reason saying “already moved” or an ordinary keep/drop does not resolve the request. Run the returned next command; changed assignments/excerpts require current-fingerprint review. Neither collection nor `APPLIED_PENDING_REVIEW` is final semantic acceptance.

Use `lookup --as-file` and the host's file-reading tool on the returned `readable_source_file` to avoid shell decoding and long-line truncation. This mode creates content-addressed UTF-8 evidence copies under `run/lookup_contexts`; it never changes source data, reviews or workflow state. `source_file` remains the exact canonical JSON for programmatic compatibility. The full canonical text and offsets are unchanged. Do not edit these evidence copies or write temporary scripts to reassemble source text. The default lookup stdout API remains available for compatible programmatic callers.

Native tasks point to a guarded `readable_input_file` (`worker-N.input.json`) instead of asking the model to read long JSONL lines. It is a lossless reading view of the same input; collection still uses the original guarded JSONL. Ordinary values are unchanged. An overlong string is represented as `_readable_text` with `length`, empty `join`, and ordered `segments` containing `start`, `end`, `text`; concatenate those text values without separators to recover the original string. Offsets are local to that field, not automatically source offsets. Read the entire view, continuing by line offset when the host paginates. Never treat a truncated preview as complete evidence. The script supplies this layout; do not create helper programs to reformat the packet.

At final excerpt review only, the reading layout omits the script-owned `review_fingerprint`, the four known review hints (`short_excerpt`, `target_review_required`, `work_consistency_review_required`, `cluster_claim_review_required`) only when exactly boolean false, an exactly empty `promotion_markers` list, and exactly empty `context_before`/`context_after` strings. The task states these known missing defaults explicitly. True hints, nonempty/unknown/ill-typed values, every evidence segment, aspect term, title and meaningful context remain literal and unchanged. Original machine rows, templates, fingerprint binding, guard hashes and all ordinary final validators are unchanged; there is no auto-keep or omitted semantic requirement.

Each task file includes the current stage's actual semantic rubric. Children do not read program source, scan folders, or reread unrelated references. Read the assigned candidates first, then batch genuinely necessary full-text lookup IDs into one call. The parent passes the returned short prompt unchanged; it need not rewrite the child instructions or repeat the rubric 16 times.

After all children return, execute the returned `collect_command`. `REPAIR_REQUIRED` lists only the incomplete worker files; resume those workers to fill the reported gaps, then collect again. Successful workers are not rerun. `STALE` means an input changed while workers were active: do not bind old answers to it; advance and use the new packets. Collection is not semantic acceptance. After `COLLECTED`, execute `next_command` to let the normal controller validate evidence and continue.

For final-review omissions or container/decision conflicts, collection lists exact `missing_view_ids`, `unexpected_view_ids`, `overlapping_view_ids` and `incomplete_review_ids`. `repair_readable_input_file` contains only affected assigned items, their complete current evidence/errors, current submissions and blank reserved review fields. If multiple scoped contexts fit wholly within 40000 UTF-16 units, `combined_repair_readable_input_file` provides one complete small tail with each item's worker and original output path; otherwise all original scoped files remain, without clipping. Read this tail instead of entire material packets, plus each current output file before editing. Repair only listed IDs after the corresponding native task ends, preserve other answers and keep a single writer per output. Missing decisions remain undecided; no source is deleted, guessed or approved. Normal full coverage, input guards and final validation still apply.

Normal `review-wait` and `review-status` CLI output uses per-worker response counts instead of repeating every pending source ID on each poll. Errors, parent-decision IDs and completion/acceptance warnings remain explicit. If exact pending IDs are genuinely needed, run the returned `detailed_progress_command` (`review-status --details`); `review-wait --details` and the programmatic progress API also retain the complete lists. This changes display only, never submission coverage, semantic gates or review data.

After `STALE`, never copy old worker overrides into a new dispatch, even when source IDs match. Candidate indexes belong to their guarded packet and may now identify different passages. Existing successful work is reusable only when the controller itself preserves its current binding; new packets require reading their current evidence.

For a definitions-only assignment redispatch, the controller may expose a `prior_proposal` in the new guarded item. It is a previous AI proposal that passed field/verbatim preflight, not an approved current judgment. A separate owned, hash-checked checkpoint retains complete old definitions and expanded literal evidence, never old candidate indexes. This is available only within the same workflow with byte-identical source pools, configuration, scripts and reference rules; selected definitions must be completely unchanged. Removed definitions, reordered old catalogues, changed selected semantic fields or corrupt/missing checkpoints fall back to ordinary full judgments. Complete added/changed competitor definitions are shown, including fields omitted from the short choice catalogue.

The reading view references a proposal's repeated exact evidence using this item's current evidence-menu indexes where unambiguous; otherwise it retains the literal text. Complete selected definitions and definition changes are presented once per worker in `contract.prior_proposal_definitions[batch]`. This is only lossless reading layout: the original guarded machine item retains the full old proposal and literal positions, and the collector never reads a projected answer or reuses old menu indexes. Secondary evidence remains literal under its ordinary contract.

Read the current evidence, previous proposal, selected definition and `current_definition_changes`; check whether any added/changed competitor fits better and whether target, aspect, local stance and complete meaning still support the proposal. Only if still agreeing may the worker replace this ID's entire editable value with exactly `confirm_prior_proposal` (the item's current token), `checked_current_competitors: true`, and a source-specific current `reason`. There is no prefilled confirmation. An untouched template, old token, empty reason, integer instead of boolean, mixed confirmation/full-answer fields or another source's token is rejected. Otherwise submit a full new judgment or a parent decision. Display-exclusion proposals likewise require explicit current review, never automatic carry-over. The collector restores only explicitly confirmed literal fields, then runs the same ordinary validation and controller advance; final excerpt review is never bypassed. This avoids rewriting unchanged fields, not the current semantic confirmation, and has no proven model-time saving yet.

The literal-only cache at `run/native_assignment_evidence_cache.json` remembers only verified literal passages and target-evidence text, including successfully checked items from a batch that still needs repairs. This is not a review ledger: it contains no cluster, stance, decision, reason or old candidate index. New packets may append those exact fragments as evidence-menu options only within the same workflow and unchanged full source hash. Positions are rechecked against current source text; extra local context is supplied, duplicate options are omitted, and added reading material is capped at 1200 UTF-16 units per item. Overlong hints are omitted whole, never truncated or used to exclude a source. The immutable new worker input guards the resulting menu. Workers must read current definitions and explicitly choose all new semantic fields unless the separate guarded prior-proposal path above provides an explicit current confirmation. Other workflows and changed source text cannot use either cache or prior proposals.

Changing cluster definitions invalidates the current assignment dispatch immediately. The parent must combine all additions and term repairs into one write to `cluster_definitions.json`, or apply them sequentially with a reread between writes; never launch parallel edits against that file. Reread once to confirm every intended cluster ID and term is present, then run `advance` and use the newly prepared state before repairing any worker answers. Do not spend another pass correcting files that can no longer be collected.

The parent does not reread or copy all worker answers. Controller-rejected items remain in the next packet with field-level errors; repair only those. When the stage changes, follow its normal operator contract. Cluster discovery, cluster-definition changes, set/count review and final visual inspection belong to the parent. Completion still requires COMPLETE and verification PASS.

Assignment collection errors include `repair_readable_input_file` containing only the failing rows, their current submission and exact errors. Read that instead of the whole worker input; edit only the listed `repair_source_ids` in the original `output_file`. The optional `parent_decision_readable_input_file` groups no-fitting-cluster responses for the parent, without accepting or excluding them. Machine JSONL counterparts remain available as `repair_input_file` and `parent_decision_input_file`. These context files are read-only views, not new dispatches or review submissions; the unchanged original guards and full-coverage checks still apply on collection.

For `cluster_assignment_review`, the controller distributes the unresolved source IDs in packets of normally 12 items per worker (at most 14 when the entire small tail fits), with frozen current cluster choices and the existing override contract. This scheduling rule depends only on queue size and worker count, never a particular period or work. Explicit `--per-worker 12` preserves the smaller fixed cap. Children may choose a cluster, select verbatim passages or give evidenced display exclusion; they cannot change cluster definitions. `NOT_APPLICABLE` means the current stop is a schema/binding repair rather than a JSONL residual packet: the parent follows its ordinary operator contract. A genuine viewpoint with no fitting cluster must come back to the parent for a definition decision, never become an automatic exclusion. Source and excerpt transport failures are also reported against their exact worker; successful workers are not rerun.

A freshly generated, entirely untouched assignment form remains a pending JSONL packet during status checks and dispatch. This is not approval: every item still needs an explicit evidence-backed review. Any edited or malformed submission continues through the ordinary validation path.

Assignment workers can select `passage_candidate_indexes` and `target_evidence_candidate_index` from their guarded inputs. The collector backfills only the chosen exact source text and positions; the worker still explicitly supplies the cluster, local stance and source-specific reason. Conflicting text/index submissions, invalid indexes and ambiguous source locations are rejected. If no candidate supports the judgment, use the ordinary verbatim evidence fields after lookup and clear the corresponding index. Workers do not repeat JSON checks, substring checks or position calculations; collection performs these and reports exact failures.

Explicit `passage_stance` is required for every selected native assignment, including ordinary fields and empty-index submissions; a selected secondary cluster likewise needs `secondary_passage_stance`. These are AI judgments, never copied from the cluster label by the script. Missing stance is returned with the source's repair context before merging, so it does not silently fall back to keyword inference on the next advance. Evidenced exclusions and no-fitting-cluster responses retain their separate contracts.

An explicit `__exclude__` has no selected-cluster stance to fill, whether its evidence is indexed or written verbatim. It still requires the normal legal `exclude_reason_code`, source-specific reason and continuous original exclusion evidence. A worker may explicitly select `exclusion_evidence_candidate_index` from `passage_candidates`; the script restores only that chosen exact text, never decides exclusion or repurposes another evidence field implicitly. Missing reason codes, invalid indexes and conflicting rewritten evidence still fail. No-fitting-cluster responses remain parent decisions, never automatic exclusions.

Passage evidence and target-work evidence are separate families: `passage_candidate_indexes` corresponds to `passage_fragments`/positions, while `target_evidence_candidate_index` corresponds to `target_evidence`. Both families can coexist and may be needed together. Target evidence cannot replace the opinion passage. Follow each error's precise `issue`, `field` and `required_fix`; a missing stance is not a verbatim-text failure and must not trigger an unrelated evidence rewrite.

Within an assignment input row, `current_passage_candidate_index` and each top candidate's `passage_candidate_index` refer to that row's `passage_candidates`. Repeated exact text appears once; all cluster candidates, scores, hints and original passage text remain available. Non-indexable passages keep their inline text. These references do not endorse any candidate.

During final review, `display_candidate_outside_routed_window` means rendering selected text outside the earlier routed passage. A title naming the target work cannot by itself establish attribution for this different paragraph. Review the displayed local context and the supplied target evidence; recut or reject when it concerns a different topic. The flag does not automatically discard the source.

`cross_section_context_review` flags a possible carry-over from a preceding section: the preceding context's last bracketed title differs from the target, and the displayed raw excerpt crosses a section marker before introducing the target. Read that context and check every displayed segment, not only the later segment selected as evidence. Recut an unrelated leading passage; a genuine comparison may remain with an evidence-backed explanation. This title hint is not proof of misattribution and never authorizes automatic exclusion. For short excerpts, concrete support must explain the current aspect: role counts or release dates alone cannot establish plot quality, acting quality or visual quality.

At eligible review gates, `operator_contract.native_review` repeats the host-capability condition and exact `dispatch_command`. Use this entrypoint after a checkpoint resume as well; do not invent a second dispatcher or fill the parent file while children are active. Hosts without an inheriting native Agent retain the ordinary serial packet path. The hint does not launch models or relax validation.
